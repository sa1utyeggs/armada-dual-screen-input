# Targeted lower coordinate capture

This GPL-2.0-only helper is excluded from application bundles. It opens its own native lower X11 window, observes manual touches and reads the physical `bottom_touchscreen` evdev stream without a grab. It sends no input, transforms no recorded coordinate, and adds no motion filter. It does not manage services, modules, boot files or controller registers. Parent experiment licensing/provenance remains in [the driver directory](../README.md).

Before running, verify that X display `:2` still belongs to the lower Gamescope session and arrange the input panel's preservation/restoration separately. The display argument is deliberately explicit; this prepared helper rejects another display. The lower display must remain on. Use an existing fresh output directory and run with the installed Thor Python/runtime:

```bash
python3 -B window.py /tmp/fresh-capture-a --display :2 --target A --language zh-CN --trace-required
```

UI language is explicit and defaults to English. The window bootstraps only the installed application's lower-session environment; it does not import its gesture, positioning or input-sending logic. `ready`/the `mapped` log event identify the owned window. Verify its content and placement before asking the operator to touch it.

The operator holds the blue target with finger 1. Its GDK sequence becomes the primary identity and is never replaced. A `capture-request` marker then lets an external bounded passive tracer start; that launcher writes `trace-ready` only after trace setup succeeds. The window records a three-second one-finger baseline, asks for finger 2 on the orange rail, then requests ten seconds of vertical sliding. The first contact must stay held; the second can lift/recontact, with each identity recorded. The window writes `capture.done` at scan end or invalidation; pass that path to the tracer's `--done`. Tracing and panel restoration remain the launcher's responsibility. Start the tracer on the marker, not while waiting for the human, to preserve the short capture budget.

Optional `--post-hold-seconds 3` adds a final control; the default is `0` and preserves the earlier A/B protocol. After sliding, the window asks the operator to lift only finger 2 while finger 1 remains held. It waits at most ten seconds, records a further three-second single-contact baseline, then asks for all fingers up. A returning second contact or early first-contact lift invalidates this control. `capture.done` is delayed until the final baseline finishes. The collector's 30-second/32 MiB limits remain unchanged; delayed operator actions can therefore abort the capture instead of extending it.

Optional `--scan-mode stationary --post-hold-seconds 3` replaces continuous sliding with three fixed-position holds: orange top `(950,300)` → bottom `(950,900)` → top again. Each hold requires three seconds with the secondary GDK coordinate inside an 80-unit radius of the highlighted point; departing or lifting resets that hold timer. Each position allows up to six seconds to reach the target, followed by a full three-second hold, with a nine-second overall maximum. Departing does not restart the original travel budget. The primary identity must stay held; extra contacts invalidate the run. Radius checks only gate this diagnostic protocol: logged GDK/physical coordinates are unchanged and no motion compensation is applied. A three-second final single-contact control remains mandatory. The same 30-second/32 MiB capture bounds apply. Phase and status records retain the current point index and target coordinates, including repeated attempts.

Optional `--continuous-secondary` additionally requires the same second-contact GDK identity throughout all three stationary points, until the prompt to lift finger 2. Its lift or replacement during travel/holding invalidates the sequence. The window explicitly asks the operator to slide along the orange line without lifting. The default is off, preserving the earlier recontact-permitted protocol; this option is rejected outside stationary mode. Readiness metadata records the option and the 6/3/9-second stationary budgets, while phase/status records retain the fixed secondary identity.

`launch_capture.py` provides only that passive trace coordination. In a separate process, start it before the operator touches the ready window:

```bash
sudo python3 -I -B launch_capture.py /tmp/fresh-capture-a
```

The absolute directory must already belong to the non-root operator identified by `SUDO_UID`; an old marker/trace or symlink directory is rejected. The launcher waits up to 600 seconds by default for `capture-request`, starts the sibling passive collector with its existing 32 MiB bound and a 30-second duration, and allows five seconds for trace setup. `trace-ready` is written only after the collector reports successful setup. A successful exit must also confirm removal of the collector's private trace instance and observe `capture.done`. A failed or prematurely ended trace writes `trace-failed`, which invalidates the window with a bilingual explanation. `trace-result.json` retains bounded collector stdout/stderr, exit status and cleanup outcome. Files written through sudo are assigned to `SUDO_UID`. Cancellation/signals terminate only the private collector child, with a three-second graceful wait and two-second kill fallback. The launcher does not manage the panel or any other service; arrange panel restoration separately and verify its result. No individual process wait exceeds five seconds.

Both `window.py` and `launch_capture.py` accept `--wait-seconds N` in the range 1…600, defaulting to 600. The window has a separate 50-second active budget starting when it issues its first capture request. Waiting does not consume that active budget, and repeated requests cannot restart it. A valid first touch observed before the waiting deadline may be processed on the next UI tick without losing its full active budget. Window readiness/status/request records retain both budgets and deadlines; the launcher records its wait, 30-second capture and setup budgets separately. A first-contact timeout and an active-window timeout have distinct diagnostic reasons. The collector's 30-second/32 MiB limits are unchanged.

Run A uses the stationary target `(260,760)` and run B `(260,540)` in a 1240×1080 reference canvas. The secondary rail is at x=950, y=300…900 in both. Prior recordings showed raw X approximately mapping to inverted native-window Y, but the new raw/UI records must verify that relation again. Changing only the stationary target's Y tests whether an anomalous raw-X region follows the first contact or stays at an absolute screen location. Separate fresh directories and full release between A/B are required. These targets are an experimental control, not an assumed universal fault boundary.

`window-events.jsonl` records unmodified GDK coordinates/source timestamps, read-only Type-B snapshots at every SYN_REPORT, and phase changes. Raw source timestamps retain evdev's existing clock; each record additionally has host monotonic `at`, with a realtime/monotonic pair at setup. Initial slot axes are queried before touching; cached axes persist across contact-ID changes. SYN_DROPPED, an ambiguous physical node, extra contacts, early primary release, display-off or time limits invalidate the run rather than silently repairing missing data. `status.json` exposes current phase/identities; `done` marks window exit. No saved user settings are changed.

Offline checks cover event-cache semantics, identity/phase guards, bilingual keys/placeholders and collector coordination/failure cleanup using private fake subprocesses. Linux GTK/Pango rendering, lower focus/placement, real trace coordination and hardware behavior still need device verification; a Mac unit-test pass is not that verification.
